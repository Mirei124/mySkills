# Hypha — 设计意图

> v0.8（2026-08-28）｜本版在 v0.7 上补上：证据引文定位、`claim_kind` 替代 `author` 豁免、`triggers` 独占机器路由、`lint --audit` 的关系／路由候选、草稿经 `apply` 原子发布，以及不再用 mtime 伪造发生时间。
> 本文件只承载**为什么**与**是什么**。实现细节见 `spec.md`（尚为 v0.3，正在按本版重写）。评审裁决见 §附录、§附录二。

## 0. 一句话

一个本地的、agent 维护的**任务与知识统一层**：来源不可变、断言必溯源、启动成本与语料规模无关；任务与知识是同一种 markdown 文件，靠双链互相到达；追加式快照日志无条件记下每一次变更，随产品仓库一起同步；HTML 是它的只读投影。

## 1. 为什么反转：只读集成比替代更贵

v0.2 的立场是「不重写 task-forest，只读它的 exports」。这条立场产生了四样复杂度，**没有一样服务于用户价值**：

1. **内容寻址锚点**（`TF-0007#req-a3f91c`，sha256 前 6 位）—— 只因 task-forest 的 `requirements` / `assumptions` 是无 ID 的字符串数组，无法稳定引用
2. **导出滞后检查** —— Hypha 读 `exports/`，task-forest 的权威数据在 `graph/`，必须比对 mtime 并提示用户先跑 `export`
3. **双锁锁序纪律** —— 「永不同时持两把锁，顺序固定为读 exports → 释放 → 持 hypha lock → 释放 → shell out」
4. **proposal 无法自封** —— 导出里没有任何 hash 字段（实测 `graph_hash present: []`），Hypha 只能生成不含 `base_graph_hash` 的 proposal 再 shell out 给对方 CLI 盖章

同时，实测显示**被替代物远小于预期**：

| task-forest schema | 定义 | 实测用到 |
|---|---|---|
| 节点类型 | 9 种 | **2 种**（`global_task` ×1、`task` ×8）|
| 状态 | 8 种 | **2 种**（`in_progress` ×1、`done` ×8）|
| 边类型 | 8 种 | **1 种**（`child_of` ×8）|
| 节点字段 | **30 个**（`graph/nodes.json` 的并集；导出多 3 个派生字段 `children`/`primary_parent`/`derived_progress`，故 33）| **10 个携带信息**（`id`/`title`/`status`/`progress`/`summary`/`kind`/`difficulty`/`estimated_total_minutes`/`created_at`/`updated_at`）。**13 个全空**；**4 个全库常量**（`confidence`=0.6、`priority`=3、`progress_source`=manual、整个 `alignment`）——常量即无信息量；另 3 个仅 1/9 非空（`requirements`/`acceptance_criteria`/`evidence`）|
| `alignment` 子字段 | 6 个 | **0 个**。看似 9/9 已填，实为占位默认值：6 个子字段在 9 个节点上各自只有一个取值（`fit`=`unknown`、`fit_confidence`=`0.0`，其余空串/空数组）|
| 下游消费者 | gap-router、local-agent-control-room | **0 个**（均未安装）|

3232 行代码、9 个节点 1.2MB 导出。结论：**固定的接线成本 > 实测的替代成本。** 反转不是朝令夕改，是拿到测量之后的结论。

> **这些数字由脚本产出，不由记忆产出**：`tools/measure-task-forest.py <task-forest 目录>`。加它的直接原因是 codex 评审发现本表原先写「33 字段 / 8 个携带信息 / 12 个全空」——33 是**导出**的字段数（含 3 个派生字段）而非节点 schema 的 30，`parent` 根本不是节点字段（它在边表里），全空是 13 个。口述的测量不可复核，等于没有 `anchors:`（法则二）。分母也因此拆开写：**schema 字段数 / 全空数 / 常量数 / 携带信息数**是四个不同的量，混用会让「用量极低」这个结论显得比实际更强。

> **可反驳条件已部分触发。** 上面这条论证明说了它的失效方式：「如果哪天真的用上了 `depends_on` 网、8 种 kind 和时间轴回放，它就失效」。其中两项现在被明确要求了（依赖 DAG 用于规划、时间轴回放），v0.6 又把追加式变更日志恢复了回来。重算：被替代面从「1 种边、2 种状态」扩到「2 种边、5 种状态、时间轴、DAG 视图、变更日志」，仍远低于 9 kind／8 状态／8 边／30 字段，且四项接线成本与 0 个下游消费者不变。**结论不变，但余量连续两版变窄**——第三项（8 种 kind）若也被要求，就该重新算一次，而不是继续沿用这段话。

## 2. 三个来源，各取一样

| 来源 | 取走的那一样 | 没取的 |
|---|---|---|
| **Nocturne Memory** | `disclosure`——每条记忆自带人类可读的「**何时读我**」，使启动只加载当下相关的部分（96.9 万字库首条消息只载 7.2K）| 图数据库、URI 图谱、人格/身份平面、MCP server、豆辞典 |
| **LLM Wiki**（karpathy）| 不可变 `src/` + LLM 独占维护的 markdown + **查询答案回填成新页** + **`[[双链]]` 与红链待办** | `log.md`（要求每次操作手记一笔，正是「会忘记更新」的形态，见 §5）、`index.md` 全量索引、Obsidian 工作流依赖 |
| **task-forest** | **森林结构与状态度量**（单主父树形、状态机、进度）+ **依赖 DAG** + **构建过程回放** + **追加式变更日志**（v0.6 恢复，见 §3）+ **单文件离线 HTML** | proposal 两条车道、全量快照副本、序号管理、全局 SQLite 注册表、20 个未使用字段、以及它 HTML 的内嵌预渲染式实现 |

**融合的理由是缺失互补，不是形状相似**：task-forest 有度量但对知识失忆；LLM Wiki 有溯源但无路由（作者自承 ~100 sources 撞墙）；Nocturne 有路由但无锚点（断言不可证伪）。三个空洞刚好错开。

> v0.1 曾用「两个项目都收敛到图后端/树前端，所以这层抽象是对的」来论证融合。**这条论证已撤回**：那是任何带交叉引用的层级数据的默认结局（文件系统+软链、DOM+超链、git DAG+branch 全是这句话），不构成理由。
>
> 但撤回时给的替代理由——「任务的边是**承诺**（成环是 error），知识的边是**观察**（成环无害）」——从 v0.5 起是正面的设计规则，而不只是一条反驳。它直接生成了双链的两套校验制度，见 §6。

## 3. 三条法则

### 法则一：路由
`when:` 是人读的「何时读我」说明，**不参加机器匹配**；机器只匹配 `triggers:`。缺省的 `triggers` 由标题与 `when` 自动抽取，agent 只在自动结果不够时补词。启动时按当前话轮/变更文件/在跑任务匹配 `triggers`，只交付命中项的**路径、`when` 与 `triggers`**，正文由 agent 按需自己 `Read`。这些字段必须按不可信数据展示，不能被拼成可执行指令。这是启动成本与语料规模解耦的全部机制。

任务节点不写这两个字段——它们进 boot 的依据是状态（在跑/受阻/可开工），不是话题相关性。**这是任务与知识唯一的语义分歧。**

### 法则二：溯源
知识按 `claim_kind` 而不是 `author` 决定证据义务：`sourced` 必须有 `anchors:`，并带逐对写明 `{anchor, quote}` 的 `evidence:`；quote 必须能在自己的 anchor 段落中逐字找到。`inference` 必须显式写 `inference` 并列出前提来源或知识页；`note` 可以无证据，也无需 `when`，但默认不参与 boot 路由。CLI 校验证据位置和引文存在，不替 LLM 判断自然语言蕴含。

### 法则三：审计由两个机制分工，谁也替不了谁

`.hypha/` **由产品仓库跟踪**（`.gitignore` 里那条 `.agent-workbench/` 是旧位置，新目录不适用）。这样一次 `git push` 同时带走代码与状态，多机器同步不需要第二个 remote。

代价是 **hypha 不能自动提交了**——往用户的功能分支塞几十个记账提交、跟暂存区抢 `git add`，是替用户做不可逆决定。v0.3/v0.4 的「不做自动 commit」因此**恢复原判，且理由和当初一模一样**；v0.5 曾以「独立仓库里无人协作」为由翻掉它，那个前提现在没有了。

于是 git commit 重新变成**有条件**的（人想起来才提交，而且会把一次会话的几十次变更压成一个提交）。这个洞由 hypha 自己的快照日志堵上：

**并且必须挑明一件事：任务层从此是分支作用域的，这是产品语义，不是缺陷。** 我原先把它写成「代价」并说「没有好的缓解」，那是在同时宣称「状态随代码同步」和「任务层连续」——codex 指出这两句不能都成立，它对。选定的那句是前者：

> **一个任务属于它被创建的那条分支。** 切到任务创建之前的分支，它不存在；合并分支，它随功能一起并进来。

这不是妥协出来的说法，它在多数时候恰好是对的语义：任务是「这条分支要做的事」，功能合并了任务就该合并，功能被丢弃了任务也该跟着消失。真正被牺牲的是**跨分支的长期任务**（那种「无论在哪条分支上都还欠着」的事）。它有一个明确去处，不需要新机制：**`~/.hypha/` 是全局作用域**，跨分支、跨 repo 的任务放那里。于是作用域变成一个**显式的二选一**（workspace = 随分支走 / global = 不随分支走），而不是一个隐藏的坑。

代价里剩下真的没有好答案的那部分，是 frontmatter 的合并：两条分支同改一个任务的 `status`，git 会报文本冲突，`merge=union` 对此无能为力（它只管日志行）。缓解是把字段拆细（一行一个字段的 YAML 更容易合），根治没有。这条进 §12，且验收里必须有分支切换/合并/丢弃三个用例（§11）。

| | 产品仓库的 git | `.hypha/snapshots/` |
|---|---|---|
| 谁写 | 人，有条件 | hypha，无条件（§9⑥）|
| 粒度 | 一个提交 ≈ 一次会话 | 一行 ≈ 一次变更 |
| 记什么 | 代码 + 状态的**并置** | 只记结构与状态的**变更** |
| 不可替代之处 | 把「哪次代码改动对应哪个环节」钉在一起；顺带解决同步 | 无条件、细粒度，且不依赖人记得提交 |

**这里我删错过一次。** §10.1 曾以「`.hypha/` 的自动提交给出同样的无条件 append-only 语义」为由删掉 task-forest 的 `events.jsonl` + `snapshots/`。那句话只在 hypha 拥有仓库时成立；现在不成立，所以它得还回去——但**还回来的是语义，不是实现**，见 §10.1 那一行的重写。

唯一的写入纪律仍是**不原地销毁**：退休一条断言 = 置 `status: superseded` + 写 `superseded_by`，不删文件。

## 4. 任务与知识是同一种文件

```
know/api/rate-limit.md     ── frontmatter + markdown 正文
intent/0007-oauth-flow.md  ── frontmatter + markdown 正文
```

同一个解析器、同一把锁、同一个 git 历史、同一个 lint、同一套双链。差别只在：

| | know | intent（任务）|
|---|---|---|
| 进 boot 的依据 | `triggers` 与话轮/变更文件的匹配度；`when` 只作说明 | 状态（`in_progress` / `blocked` / 可开工）|
| 必填的路由字段 | `claim_kind`；`when` 只对非 `note` 必填 | 无 |
| 关系 | 正文 `[[链接]]`，**观察边** | `parent` + `depends_on`，**承诺边**，校验单父/无环/无悬空 |
| 标识 | 路径 | `id`（四位序号）|
| 状态取值域 | `active` / `superseded` | **5 态**：`todo` / `in_progress` / `blocked` / `done` / `dropped` |

`id` 存在的理由有两条，都和「路径会变」有关：任务标题随 scope 演进而改名（知识主题不会），所以引用要用 `id`；时间轴要跨改名追踪同一个任务，也只能用 `id`（§5）。

状态从 8 态砍到 5 态：`proposed` 与 `ready` 的差别（「想到了」对「可以开始」）可从 `depends_on` 是否全部 `done` 推导；`archived` 是 `done` 的老化，git 有时间；`review_needed` 的语义由 `conflicts` 承载，且挂在知识侧更准——是知识与任务对不上，不是任务自身出问题。**这个数字在 §9 会再次起作用**，两个决定互相加强。

**这就是「完全替代」反而让设计变简单的地方。** task-forest 的 proposal / snapshot / events / SQLite 全部是为了给一份人读不了的 JSON 数据库提供审计与回滚；markdown 加自己的 git 天然具备这四样。唯一 git 给不了的是**图校验**（单主父、`parent` 无环、`depends_on` 无环、引用不悬空），这是全设计里唯一必须从 task-forest 搬过来的机制。

## 5. 投影：HTML 与时间轴

### 为什么保留 HTML

v0.3 曾以「权威数据是 markdown，人直接读」为由放弃。**这条理由只覆盖了内容可读性，漏掉了结构可见性。** 逐个读 500 个文件，永远看不出森林形状、依赖 DAG、状态分布、以及 open 冲突聚在哪。

但它存在的理由和 task-forest 的不同：那边是**权威数据不可读**，这边是**形状不可见**。所以它显示的重点是 markdown 显示不了的——森林与深度、依赖 DAG、双链关系网、`affects` 跨类连线、未锚定与未提交的位置、时间轴。

三条结构性约束（**不是体积约束**）：

1. **纯投影。** 可从 markdown 与 git 完全重建，删掉不损失任何信息。因此进 `.hypha/.gitignore`。
2. **只读。** 不能在 HTML 里改状态，不做回写。它是视图，不是编辑器。
3. **不许给 schema 加字段。** 某个视图想多存一个字段，那是视图的问题，不是数据的问题。这条是防可视化反向污染数据模型——task-forest 的 `status_legend` / `edge_type_legend` / `edge_type_counts` 正是导出结构倒灌进 schema 的例子。

### 形态：单页面、内嵌原文、客户端渲染

单页 HTML，点节点即看到该节点 markdown 的美化渲染。实现上内嵌 **markdown 原文** 加一个极小的渲染器，而不是内嵌预渲染 HTML：

- **必须离线双击可开。** `file://` 下 `fetch()` 被浏览器 CORS 拦截，所以「按需加载 md 文件」的方案在本地打开时根本不工作
- 内嵌原文比内嵌预渲染 HTML 小（省掉标签膨胀），渲染器只需覆盖实际用到的子集（标题、列表、代码块、链接、强调、表格）

因此 v0.4 写的「一个节点 ≈ 200 字节、500 节点 ≤200KB」**作废**——正文要能看就必须带上正文。防膨胀改由上面三条结构性约束承担；因为它被 gitignore，重复权威数据不产生版本代价。

### 快照与时间轴：追加式变更记录，不维护变更文件

要求是「模型能知道项目怎么一步步搭起来、每个环节是什么」，且**不能靠一个 md 文件记变更**（易错、易忘）。

数据源是 `.hypha/snapshots/YYYY-MM-DD.jsonl`，**由 hypha 在每条命令入口无条件追加**（§9⑥），人从不手写、也从不编辑。

**快照是能力，不是存储形态。** 存的是每次变更一行，任意时点的全量状态由重放得到。不存全量副本：**task-forest 给 9 个节点存了 25 份全量，533KB，平均每份 21.3KB**（`tools/measure-task-forest.py`）——按这个比值，500 节点一份就是 MB 级，一次会话几十次不可接受，而这些字节现在由**产品仓库**付。

#### 先定权威：磁盘赢，日志只是审计

这一条必须写在所有性质之前，因为不定它，后面每条都是空的。codex 的攻击是对的：日志重放成 `done`、磁盘被 Write 成 `blocked`，谁赢？

> **`frontmatter` 是当前真相，快照日志是审计记录。日志永不回写磁盘。**

选它而不选反过来，是因为反过来会推翻整份设计的前提：如果日志是权威，磁盘上那份 markdown 就成了缓存，而「人和 agent 直接读写 markdown、不需要经过任何进程」是 §4 与法则一赖以成立的东西。日志赢意味着 Write 会被静默覆盖——那就等于回到了被删掉的 SQLite。

于是重放的用途被收窄成两个，都不包括「决定现在的状态」：

1. **当游标**：重放得到「日志已经知道的状态」，与磁盘比对，**差异一律以磁盘为准补一行**。所以日志向磁盘收敛，不是磁盘向日志收敛。
2. **当时间轴**：回答「T 时刻是什么样」。

这也让「重放结果 == 磁盘」这条不变量（§11）变成**构造性成立**的，而不是需要祈祷的。

#### 四条性质

- **日志即游标。** 没有第二份状态、没有需要重建的承诺——这正是当初删掉 SQLite 的那条原则（codex 抓到的「`fired_count` 只活在 SQLite，崩溃后无法从 markdown 重建」）。
- **无全局序号，但同一写者内时间戳严格单调。** 追加时若 `now <= 本文件已有最大 ts`，就钳到 `max + 1ms` 并标 `clock_skew: true`。这是用时钟换掉序号计数器：**单调性是钳出来的，不是维护出来的**，所以没有「序号存在哪、崩溃后怎么恢复」这类问题，而时钟回拨也不会让后发生的事排到前面。
- **重放幂等，且不吃掉真实变更。** 去重键是 `(ts, origin, id, field)`——不含「新值」。原先写的 `(时间戳, id, 字段, 新值)` 是错的：`todo → in_progress → todo` 若落在同一秒，第三条会被当成第一条的重复删掉。改用 `origin`（机器/会话短 id）加上上一条的单调钳位后，**同一写者在同一 ts 对同一字段只可能有一条记录**，于是这个键唯一标识一条**物理行**，去重只删 union 合并带来的重复行。
- **合并不冲突——但只对日志成立。** `.gitattributes` 给 `*.jsonl` 设 `merge=union`，两台机器同日追加时 git 并取两侧。必须说清它**不是**什么：union 合并的是**行集合**，它不对 `status` / `progress` / `depends_on` 做语义合并。状态的合并发生在 frontmatter 上，走 git 的普通文本合并，**会冲突**（见 §12 首行）。

三个剩余的定义空缺，一并钉死，否则实现者只能猜：

- **同一毫秒、不同 `origin`** 的两条记录，顺序**真的无定义**。接受，因为按上面的权威规则它不可能影响当前状态；时间轴上并列显示。
- **`YYYY-MM-DD` 按 UTC 切分**，不按本地时区。否则两台不同时区的机器会把同一逻辑日写进两个文件，`merge=union` 帮不上。
- **数组字段先规范化再比对**（`depends_on` / `affects` 排序去重）。否则顺序变化会让每次扫描都追加一条假变更。

#### 记什么、不记什么

**只记结构与状态，正文的历史归 git。** 节点的创建/退休、`status`、`progress`、`parent`、`depends_on`、`affects` 进日志；正文只记内容哈希——**哈希只能证明「这一版正文变过」，不能恢复正文**，恢复正文是 git 的职责。

时间轴只保证 Hypha 何时观察到变更：`recorded_at` 是写日志的时刻，文件名按它的 UTC 日切分。checkout、复制和 merge 都会改 mtime，所以 mtime 不进日志。只有迁移这类已知历史事实才额外写 `effective_at`，取原节点的 `created_at`；它不参与当前状态判断。`created_at` 因此是保留字段（见 §1 表里的「携带信息」列），不进「迁移残留」。

**按 `id` 追踪，不按路径。** slug 由标题生成，标题随 scope 演进而改名，按路径追踪会在改名处断掉。

#### 时间轴能给到什么分辨率（收窄过的声明）

- **快照日志给字段级分辨率**：哪个节点、哪个字段、何时变。原先写「全分辨率」是过度声明——正文只有哈希。
- **产品仓库的 `git log` 给区间级关联**：某个提交对应的是「上一个提交时刻到这个提交时刻之间的那些日志行」。这是**区间关联，不是逐条关联**——用户可以把几十次变更压成一个提交，hypha 也拿不到未来的 commit hash。它仍是 v0.5 的独立仓库方案拿不到的东西（那时状态历史里根本没有代码），但值只有这么多。

karpathy 的 `log.md` 仍然不采用：它要求人每次操作手记一笔，而这里没有任何一步依赖人记得做。

## 6. 双链：一次扫描，四种反向关系

正向由人和 agent 写，**反向一律派生，永不手写**。这是同一个机制的四个用例：

| 正向（写） | 反向（派生） | 用途 |
|---|---|---|
| know 正文 `[[另一条 know]]` | 「被哪些页引用」 | ArchWiki 式关联跳转 |
| know `affects: [0007]`／任务正文 `[[know/...]]` | 任务的知识前提集 | 冲突影响面、零输入处置（见下）|
| intent `parent` | `children` | 森林呈现 |
| intent `depends_on` | 「做完这个解锁什么」 | TODO 规划与杠杆排序 |

一次全库扫描（500 节点毫秒级）建全部四张反向表，**不持久化**——没有缓存漂移、没有 reindex、没有需要重建承诺的状态。

**为什么反向必须派生**：手写反向链接和「用一个 md 文件维护变更」是同一个病——两处要同时改，必然有一处忘记，而且忘记时无人报错。

### 两种链接，两种校验制度

这是 §2 那条被撤回的同构论证第一次正面起作用：**任务的边是承诺，知识的边是观察**，所以同一种语法要用两套制度。

| | 知识链接 | 任务依赖 |
|---|---|---|
| 语法 | 正文内 `[[路径]]`，**带上下文散文** | frontmatter `depends_on: [0005]` |
| 谁写 | agent 用 Write（它是散文的一部分）| CLI（要查环、要校验）|
| 成环 | **无害**。A 相关 B、B 相关 A 是常态 | **error** |
| 悬空 | **是特性**——指向不存在的页 = 值得写的页，lint 列成待办清单 | **error** |

**制度不按「谁写的」分，按「指向哪个命名空间」分。** codex 指出上表有个真空：`affects: [0007]` 写在 know 的 frontmatter 里，按「知识链接」读它悬空是特性，按「任务边」读它悬空是错误——同一条边两个答案。定案如下，**判据只看箭头落点**：

> **指向 `intent/` 的链接必须解析成功（error）；指向 `know/` 的链接允许悬空（todo）。**

理由不在语法在集合性质：`intent/` 是**有限的、由 CLI 发号的封闭集合**，一个解析不了的 4 位 `id` 只可能是笔误或指向了已删节点，没有第三种解释；`know/` 是**开放集合**，指向还没写的页是正常且有价值的状态。于是 `affects: [9999]`、`depends_on: [9999]`、正文里的 `[[intent/9999-...]]` 全是 error；正文里的 `[[know/api/rate-limit]]` 指向不存在的文件是红链待办。写者是人还是 agent、字段还是正文，都不参与判断。

**「双链」因此只在解析成功的边上对称。** 说全了是：反向表由**能解析的**正向边派生，红链只出现在正向侧（`show` 里单列一节「悬空」），不出现在任何反向表里——不存在的页没有地方挂反链。这样「对称」就是可机械检查的了（反向表的边数恒等于已解析正向边数），而不是一句无法验证的口号。

悬空知识链接当作待办，是 karpathy lint 里「提到了但没有专页的概念」的直接实现，而且正好接上 `hypha ask --file`：写一条答案页去补掉一个红链。

知识链接必须留在正文而不是 frontmatter，因为**「为什么相关」是散文，抽进字段就丢了**——这也是 ArchWiki 式跳转好用的原因：链接周围的句子解释了为什么该跳。

### 依赖 DAG 用于规划

`depends_on` 的反向表给出三个可直接排序的量：

- **可开工**：`todo` 且全部 `depends_on` 已 `done`
- **被什么挡住**：`todo` 但有未完成依赖，列出挡住它的 `id`
- **杠杆**：完成后解锁的任务数，降序

`hypha next` 输出这三样，零参数。模型问「接下来做什么」，有一条命令就叫这个名字。

### 反向索引取代 `assumptions`

v0.2 最大的未解决风险是**零输入**：冲突检测要比对任务的 `assumptions`，而实测 9 个任务 `assumptions` 全空、`requirements` 仅 1 条非空。

根因不是懒，是字段性质：**已填的字段都是回溯性且自明的**（done → progress=100）；**空着的都是前瞻性且需要判断的**（假设、估时）——成本在当下，收益在未来。

反向索引改变的是**填写时机**，不是催人填表：

```
know 写 affects: [0007] 或任务正文写 [[know/api/rate-limit]]
    ← 两者都在当下有回报（boot 加权、HTML 连线、跳转可用）
任务 0007 的知识前提 = 上面两者的反向，合并去重
新来源与某条 know 冲突 → 查该 know 的反向 → 直接得出受影响任务
```

所以任务节点**没有 `assumptions` 字段**，也不需要「断言 × 任务」的两两比对。这里允许两条正向路径（`affects` 与正文链接）而不违背 §9 规则⑤，因为它们在**查询时**合并成同一条无向观察边：`show 0007` 的「知识前提」把两侧并起来去重，写哪边都得到同一个答案。

**但它们在校验时不是一回事，别把话说过头。** `affects` 是 frontmatter 里的结构字段（可被 CLI 校验、指向 `intent/` 故必须解析），正文链接是散文的一部分（Write 写、指向 `know/` 故可悬空）。合并发生在查询层，不发生在校验层。规则⑤没被违背的真正理由是：**它约束的是模型在两个命令之间选择**，而这两条路径一条是字段一条是散文，写的时候不构成选择——手边正在写 know 的 frontmatter 就用 `affects`，正在写任务正文就用 `[[...]]`。

前瞻性字段的成本没有消失，它被搬到了当下就有回报的位置。这是机制改动，不是许愿——检验方式见 §12 末行。

## 7. 目录就是结构

```
<ws>/.hypha/                 # 由产品仓库跟踪，随代码一起 push
  .gitattributes  # snapshots/*.jsonl merge=union
  src/            # 不可变来源。落盘后不许改
  intent/         # 任务。文件名 <id>-<slug>.md
  know/           # 知识。目录名就是类别
    api/  lessons/  answers/
  snapshots/      # YYYY-MM-DD.jsonl，追加式，hypha 独占写
  INDEX.md        # 路由表，任意命令自动重生成（§9⑥），不靠人记得跑 lint
  view.html       # 投影。gitignore
  lock            # gitignore
~/.hypha/
  agreements/     # boot 的不可协商段（见 §8）
  know/           # 跨 repo 的知识
  config.json
```

没有平面概念、没有 URI schema、没有 SQLite、没有边表。路径就是标识，目录就是类别。

**同步只剩一个额外目标。** workspace 的数据随产品仓库走，`~/.hypha/` 是唯一需要单独同步的东西（建议 `git init` 加一个私有 remote）。v0.5 的独立仓库方案是「每个 workspace 一个 + `~/.hypha` 一个」，这是那条路被换掉的直接原因。

## 8. `agreements/` 不是「自我」，是 boot 的不可协商段

v0.1 有一个 `self://` 平面装「身份与工作契约 + 自我校准」。**已删除。**

剩下的东西按机制而非内容定义：`agreements/` 唯一不可替代的性质是**免于召回评分、免于截断、跨 repo 迁移**。它不回答「我是谁」，它回答「哪几行无论如何都必须在场」。所以它只装工作契约，且有硬上限。

自我校准（「我系统性低估迁移任务 2.3 倍」）**已删除**，理由见附录。

## 9. CLI 的读者是弱模型

CLI 的真实成本不是它有多少行代码，是**模型为了正确调用它而消耗的上下文**。这个成本对强模型可忽略，对弱模型是主要成本。所以目标函数不是「简洁」也不是「功能完备」，是：

> **高频操作无需预先加载 SKILL.md，就能正确调用。**

### 高频面（免 SKILL.md）

| 模型想做的事 | 命令 |
|---|---|
| 会话开始，我该知道什么 | `hypha boot` |
| 接下来做什么 | `hypha next` |
| 这个节点的关系是什么（反链/依赖/前提/红链）| `hypha show 0007`／`hypha show know/api/rate-limit.md` |
| 开始 / 卡住 / 做完 / 放弃 | `hypha start 0007`／`hypha block 0007 "原因"`／`hypha done 0007`／`hypha drop 0007` |
| 进度到几成 | `hypha progress 0007 60` |
| 新任务 | `hypha add "标题"` |
| 声明依赖 | `hypha needs 0007 0005`（0007 依赖 0005，写入即查环）|
| 展开 boot 没给的相关知识 | `hypha why 速率限制` |
| 检查 / 修索引 | `hypha lint`／`hypha lint --fix`；本轮关系与路由预演用 `hypha lint --audit` |
| 发布一份草稿 | `hypha apply .hypha/.drafts/xxx.md` |
| 收尾 | `hypha close` |
| 给人看 | `hypha view` |

### 低频审议面（允许读 SKILL.md）

`hypha ingest <文件>`、`hypha ask "<问题>" --file <路径>`、`hypha migrate`、`hypha init`。

**这两张表里都没有 git 子命令，也不会有。** 索引重建与时间轴由规则⑥兜底；**提交不在兜底范围内**——`.hypha/` 属于产品仓库，自动提交等于替用户改分支（法则三）。hypha 只把提交降级成一次复制：`close` 按规则③打印一行现成的 `git add` / `git commit`（**是文本，不是 hypha 去执行**），复制与否由人决定。模型因此不需要知道 `.hypha/` 在仓库里的哪一层。

**hypha 自己不调 LLM**，它是纯存储加校验。判断（这条断言是什么、和谁矛盾、该归到哪个目录）由 agent 读 SKILL.md 后做出，再调 hypha 落盘。所以 `ingest` 是一个多轮协议，而多轮协议正是弱模型容易断的地方——这就是为什么它被划进低频面并明确允许读文档，而不是硬塞进免文档面。

### 六条规则

**① 状态是动词，不是参数值。**

```
hypha done 0007                          ✓
hypha task set 0007 --status done        ✗
```

后者要求模型知道「有个状态枚举」、「枚举里有 done」、「用 `--status` 传」——三处可错。前者只有一处。**弱模型不需要知道状态枚举存在。**

代价是命令数随状态数增长。这条正好和 §4 砍到 5 态互相加强；**如果状态涨回 8 种，这条规则就该重新权衡**。

**② 常用路径零 flag。** 任何在常见用法里需要 flag 的命令都是设计缺陷。flag 只留给罕见覆盖。位置参数优先，每个命令最多 2 个。

**③ 输出自带下一步命令。** `boot` / `next` / `close` / `lint` / `ingest` 的输出里直接给出可原样复制的命令行，**带这个 workspace 里的真实 `id`**，不是占位符。

这是最强的一条杠杆：它把 CLI 知识从**上下文**（贵，必须预先加载）搬到**输出**（即时，而且刚跑完就已经在上下文里）。**模型不构造命令，它复制命令。**

**④ 错误信息就是文档。** 调用错了，打印这个 workspace 里真实可用的正确调用，不打印 argparse 的 usage 串。判据：**每次无效调用之后的下一次必须能成功**——错误信息要足以自纠，否则模型会开始猜。

**⑤ 一件事只有一条路。** 划清：

> **需要分配 `id`、查环或发布正式节点的走 CLI；正文先写草稿，再由 CLI 原子发布。**

任务的创建、状态、父子、依赖走命令；正文仍用 Write，但只写进 `.hypha/.drafts/`，再由 `hypha apply <draft>` 发布。CLI 不接收多行正文。这条边界对弱模型可判定性高：**「改状态/改依赖 → 命令；写正文 → 草稿 + apply」**。

**⑥ 记账由 CLI 兜底，模型不负责记得。**

正文仍由 agent 用 Write 写，但只写进 `.hypha/.drafts/`；`hypha apply <draft>` 在锁内校验、原子发布、追加日志并重建索引。直接 Write 正式节点只留作兼容和救援路径，`sync` 会记住它，`lint` 会提示它没走托管发布。于是模型不需要记得哪条命令负责记账。

`done` 也不再只是一句状态声明。`close` 会把本轮改成 done 的任务的 `## 验收`、`## 证据`、关联知识和本轮改动文件并排出来；CLI 不替人批准，agent 只需基于这小段证据确认“验收确实满足”或退回 `in_progress`。

所以每条 hypha 命令（无论它自己是读是写）在真正干活**之前**先跑一次兜底：

```
每条命令入口：
  ├─ 扫 .hypha/，只解析 frontmatter（正文不读）
  ├─ 重放 snapshots/ → 「日志已经知道的状态」
  ├─ 与磁盘比对，差异一律以磁盘为准 → 追加变更行
  └─ 无条件用当前 frontmatter 重建 INDEX.md（写临时文件后原子改名）
然后执行本次命令，若产生改动则再走一次上面这段
```

四条性质让它可靠：

- **幂等。** 无差异时只是一次重放加一次 frontmatter 扫描，纯读。
- **入口无关。** `boot` / `next` / `lint` / `done` 任何一条都会兜底，所以模型不需要知道「哪条命令负责记录」——它不需要知道这件事存在。
- **迟到但不丢失。** 兼容路径里直接 Write 的变更会在下一条命令才被记录；日志只写 Hypha 观察到它的时间，不拿不可靠的 mtime 编造发生时间。
- **索引重建无条件，不看有没有差异。** codex 找到一个真实的崩溃窗口：若先追加了日志、在重建索引前崩溃，下一次重放就与磁盘一致了，**按「有差异才重建」的写法索引会永久停在旧版本**——而这正好命中 §11 那条「任意命令后 INDEX 必然一致」的不变量。重建是从 frontmatter 纯派生、成本与追加同级，没有理由省，所以改成无条件。

同一个缺口的第一个实例也是它：v0.5 之前 `INDEX.md` 靠 `lint --fix` 重生成，agent Write 完却没跑 lint 的话，**boot 会静默漏掉这个节点**——比漏记历史更糟，它直接打击主指标。

**成本必须给数字，不能写「毫秒级」。** 这是每条命令的 O(N) 前置，与 §0 说的「启动成本与语料规模无关」有张力——那句话讲的是**交付给模型的上下文**与规模无关，不是**进程内的扫描**与规模无关，两者不该混。所以它变成一条可证伪的性能要求（§11）：**500 节点下兜底 ≤50ms**。超了就退到按 mtime 只解析变更过的文件，全量校验只留给 `boot` / `lint` / `close`——但那要引入一个 mtime 水位缓存，而缓存就是第二份状态，所以**不到超标不引入**。

**覆盖面是「调用触发」，不是「写入触发」。** 说清楚免得把它读成比实际更强：hypha 不监听文件系统，一整轮会话一条命令都不调，就一行都不会记。它保证的是**不依赖人或模型记得记账**，不是**任何写入都会被捕获**。真正的残留窗口见 §12。

**兜底不包括 `git commit`。** `.hypha/` 属于产品仓库，自动提交会污染用户的分支（法则三）。hypha 能做的是让提交变成一次复制：`close` 按规则③输出带真实文件列表的 `git add` / `git commit` 命令行，`lint` 把未提交的 `.hypha/` 变更列成提示。想要自动提交的人可在 `config.json` 里 opt-in，**默认关闭**。

这条是规则③（输出自带下一步命令）的对偶：③把**知识**从上下文搬到输出，⑥把**纪律**从模型搬到程序。凡是「需要每次记得做」的机械动作，都该往这边搬——判据是它是否幂等、是否与入口无关。

### 分工判据：可计算的归程序，需判断的归模型

规则⑥是一个更普遍原则的实例。这个原则决定每一条命令该不该存在：

> **凡是确定性可计算的，封装成命令；只有真正需要语义判断的，才留给模型。**

理由不是省代码，是**稳定性**：模型调工具的结果可复现，模型自己做机械推导的结果不可复现。让弱模型去 Grep `[[链接]]` 并归一化路径变体（相对/绝对、带不带 `.md`、大小写），它每次可能给出不同答案，而且错了没人报错——这类静默错误比崩溃更贵。

逐项落位：

| 归程序（命令） | 归模型（读 SKILL.md 后判断） |
|---|---|
| 反链查找、悬空链接（红链）清单 | 这条断言是不是知识、该归哪个目录 |
| 依赖 DAG：可开工 / 被谁挡住 / 杠杆排序 | 新来源与旧条目是不是真矛盾 |
| 森林深度、子树聚合、环检测 | `when:` 该怎么写才是「何时读我」 |
| 路径归一化、`id` 分配与解析 | 一条问答值不值得沉淀成页 |
| 索引重建、时间轴重建 | 冲突属于四态里的哪一态 |
| bigram 召回与打分 | 任务该不该改状态 |

右列的共同点是**没有正确答案可以机械验证**；左列的共同点是**有唯一正确答案，而且验证它比重算它更贵**。

**「提交」从左列里删掉了。** v0.5 那版把它列在归程序一侧，那是自动 commit 设计的残留；v0.6 撤销自动提交之后，它两列都不属于——它可计算，但**不可逆且外部可见**，判断的不是「怎么算」而是「此刻该不该动用户的分支」。这类动作单独归第三档：**由程序算出内容，由人决定执行**（规则③的输出即是）。

因此新增一条命令：

```
hypha show <id 或路径>
```

输出该节点的元信息与**全部四种关系**（出链、反链、父/子、依赖/被依赖、知识前提、悬空链接），任务和知识共用——它们本来就是同一种文件（§4）。**正文不打印，只给路径**，由 agent 自己 `Read`（法则一）。

### 这条判据没有推翻「不做 read / search」

看上去矛盾，实则相反：判据的分母是**计算量**，不是方便程度。

- `hypha read` —— 零计算，纯粹是 Read 的别名。多一条命令，模型多一个要排除的分支，收益为零。**仍然不做。**
- `hypha search` —— 同理于 Grep。**仍然不做。**
- `hypha show` —— 要解析 frontmatter、归一化 wikilink、遍历四张反向表、判断悬空。这些**用 Grep 做不到**，用一串 Grep 拼凑则每次结果都可能不同。**做。**

**但「能否用一次 Grep 替代」是启发式，不是判定式，得说清。** codex 攻在了实处：「一次」没有定义（一次带 `-A`、带管道、带 `\|` 的 Grep 能顶多少？），而任何被拒的命令都能被重述成「它还要归一化，所以 Grep 顶不了」——一个总能自证的分母不是分母。它真正的作用是**举证责任的方向**：默认不加，想加的人得说出 Grep 在哪一步会给出不同答案。这足够挡住随手加命令，不足以定义边界。

### 真正的上界是命令面，不是判据

边界改由三条可机械检查的约束给出，写进 §11 的验收：

1. **命令面封闭。** 高频面是一张**穷举**的表（§9 那张），新增必须同时给出它挤掉了谁、或说明为何之前那条不够；不允许「再加一条方便的」。
2. **每条命令唯一职责，且不重叠。** 任意两条命令不得存在「两条都对」的输入——这是规则⑤「一件事只有一条路」在命令面上的形式。
3. **每条命令 ≤2 个位置参数、常用路径零 flag**（规则②）。

配一张**混淆对**表，列出成对易混的命令与判据一句话，`hypha` 无参数调用时直接打印它：

| 易混 | 一句话判据 |
|---|---|
| `next` vs `show` | 不知道做哪个 → `next`；已经盯着一个 → `show` |
| `needs` vs `add --parent` | 先后顺序 → `needs`；从属关系 → `add --parent` |
| `why` vs `show` | 找知识 → `why`；找某个节点的关系 → `show` |
| `lint` vs `close` | 想知道哪里坏了 → `lint`；这一轮做完了 → `close` |
| `progress` vs `done` | 还没完 → `progress`；完了 → `done` |

**验收把两类错误分开统计**（§11）：**选错命令**（该 `next` 却 `show`）和**参数写错**（命令对、id 或路径错）。前者由混淆对表和命令数负责，后者由规则③④负责。混在一起统计，就无法判断「命令太多」和「错误信息太差」到底是哪一个在拖分——而这两者的修法相反：一个要砍命令，一个要加输出。

### 与「命令数越少越好」的张力

规则①让命令变多（4 个状态动词 + `progress` + `add`），分工判据又加了一批（`show` / `needs` / `next` / `why`）。高频面现在是 12 条左右，比 v0.4 差不多翻倍。这看似违背「弱模型怕选择」。

我的判断是：**成本在决策难度，不在命令条数**——一个名字无歧义、只吃一个位置参数的命令，排除它的代价接近零；一个带枚举的 flag 要查一次表。而且这批命令按可达时机天然分层：状态动词只在「手里已有 `id`」时可达，`show` / `needs` 只在「已经在看某个节点」时可达，都不与 `boot` 竞争会话开头那个决策点。

**这个判断是可证伪的**，就用上面那个分项统计：如果「选错命令」的比例压不下去，说明成本确实在条数上，那就得合并命令（例如把 `why` 并进 `show`），而不是继续加输出。

**但这仍是判断，不是测量。** 结论由 §11 的验收来定，不由这段话来定——如果第一层验收里弱模型出现「选错命令」而非「参数写错」，那就是这段判断错了。

## 10. 明确不做的事

### 10.1 放弃的 task-forest 能力

「放弃」不等于「未实现」。以下是看过实测用量后决定**不做**的，每条附理由；如果理由被推翻，决定就该重开：

| 放弃的 | 理由 |
|---|---|
| proposal 两条车道（`proposal-save` / `proposal-apply` / `base_graph_hash` 陈旧拒绝）| `git diff` 是更好的事前确认，且 apply / 陈旧检查 / diff 渲染三样它全部免费提供。证据：`proposals/` 目录五天 0 文件 |
| `events.jsonl` + `snapshots/` + 序号管理 | **撤销：这一格现在是部分恢复，不是放弃。** v0.5 的删除理由是错的——当时写的是「`.hypha/` 的自动提交给出同样的无条件语义」，而那只在 hypha 拥有仓库时成立（§3）。恢复的是**语义**：追加式、无条件、可重放。不恢复的是实现——**不存全量副本**（task-forest 给 9 节点存了 25 份，533KB）、**不要序号**（时间戳加钳位足够，且全局序号在多机器追加下无意义，见 §5）、**不做陈旧检查**（没有 proposal 要拒绝）|
| 全局 SQLite 注册表 | 实测 1 个 workspace。改为 `~/.hypha/config.json` 里一个路径列表 |
| HTML 的内嵌预渲染式实现 | 改为内嵌 markdown 原文 + 客户端渲染，见 §5。语义（单文件离线、时间轴）保留 |
| 6 种边类型（`contributes_to` / `related_to` / `duplicates` / `supersedes` / `clarifies` / `derived_from`）| 实测 0 使用。弱关系由正文 `[[链接]]` 承载且更好——链接周围的散文解释了为什么相关；`supersedes` 已由 `status` + `superseded_by` 承载；`duplicates` = 合并文件 |
| 20 个节点字段（`purpose` / `desired_outcomes` / `success_metrics` / `non_goals` / `alignment` / `alignment_records` / `execution_hints` / `source_sessions` / `remaining_minutes_*` 等）| 13 个实测全空，4 个全库常量（`confidence`=0.6、`priority`=3、`progress_source`=manual、整个 `alignment`），3 个仅 1 个节点非空（`tools/measure-task-forest.py`）。需要时写进正文散文，不要 schema |
| `requirements` / `acceptance_criteria` 作为结构化数组 | 移入正文 `## 验收` 段。数组化的唯一用途是被引用，而引用需求已由 §6 取代 |
| `assumptions` | §6 的反向索引 |

### 10.2 整体非目标

- **不做人格/身份记忆。** Nocturne 的「主权 AI 人格」与工程价值正交。
- **不做向量检索、不做全文索引。** agent 已有 Grep/Read。路由只匹配标题、`when` 与 `triggers`。
- **不做 `hypha read` / `hypha search`。** 这两条是 Read / Grep 的纯别名，零计算，而按 §9 的成本模型每条命令都是模型必须排除的一个分支——冗余命令是双重浪费。`hypha show` 不在此列，它做的是 Grep 做不到的关系遍历。（§9 说明了「能否用一次 Grep 替代」只是举证责任的方向，不是判定式；这两条的理由不依赖那个判据也成立。）
- **hypha 自己不调 LLM。** 纯存储加校验，判断由 agent 做（§9 的分工判据）。
- **不自动提交产品仓库。** 兜底只写 `.hypha/` 内的文件，`git commit` 由人决定（法则三），可在 config 里 opt-in 但默认关闭。不自动改任务状态、不自动 `blocked`——那些在判据的右列，是内容判断，不是记账。
- **不做多写者并发、不做服务端、不做 MCP 封装。**
- **不做双向兼容层。** 迁移是单向的，原 task-forest 目录原地保留为只读归档。

## 11. 成功的定义

### 主指标（唯一测「值得」的一条）

> 连续两周真实使用后，`hypha boot` 推荐的 know 条目里，**≥50% 在同一轮对话中真的被 `Read` 了**。

低于这个数，说明路由无效，整个设计的前提（法则一）不成立，应当放弃而不是加功能。

同一次观测里附带统计：`affects` 或正文链接非空的 know 条目占比（检验 §6 的机制假设）。

主指标只会测出噪声，测不出关键知识被漏掉。因此另留一组很小的路由回归样本：人工把真实的「当前任务 + 话轮 + 变更路径」和它必须带出的 know 路径配对。每次改动打分或 trigger 抽取，CLI 都跑这组样本；缺一条就是回归。样本不替 LLM 判断关系，只防止已知的关键召回被悄悄挤出 boot。

### 弱模型可用性（唯一测 §9 的一条，分两层）

> **第一层（免 SKILL.md）**：haiku 级小模型仅凭 `hypha boot` / `hypha next` 的输出与错误信息，完成「挑一个可开工任务 → 开始 → 更新进度 → 标记完成 → 收尾」。判据：**无效调用 ≤1 次，且每次无效调用后的下一次必须成功**。
>
> **第二层（读 SKILL.md）**：同一模型读过 SKILL.md 后完成一次 `ingest`，产出的 know 节点通过 `lint`。

**无效调用必须分两类记**（§9）：**选错命令**与**参数写错**。第一层不达标时，两类的比例直接指向不同的修法——「选错命令」多说明命令面太宽或混淆对表没写对，「参数写错」多说明规则③④没做到。合并统计会让这两条路都无法证伪。

第一层不达标说明规则③④或命令面有问题，而不是「小模型不行」；它也是 §9 末段那个张力的裁决者。

### 机械不变量

> **双链对称性（只在已解析的边上）**：若 A 的正向表含一条能解析到 B 的边，则 B 的反向表必含 A；反之亦然。悬空链接只出现在正向侧与红链清单里，不出现在任何反向表里，因此「反向表边数 == 已解析正向边数」可直接断言（§6）。
>
> **权威：磁盘赢。** 绕过 CLI 手改一个任务的 `status`，跑任意一条命令，磁盘上的值必须原样保留，且日志新增一行指向该值。**日志重放的结果任何时候都不许写回磁盘**（§5）。
>
> **兜底可靠性（测 §9⑥）**：任意命令执行完毕后，重放 `snapshots/` 得到的状态与磁盘 frontmatter 逐字段相等，且 `INDEX.md` 与全部 frontmatter 一致。构造方式：绕过 CLI 直接写一个 know 文件并手改一个任务的 `status`，然后只跑 `hypha boot`，检查两者都已进日志与索引。**崩溃变体**：在追加之后、重建索引之前杀进程，下一条命令必须把 `INDEX.md` 修回一致。
>
> **重放确定性（测 §5）**：同一天的两份 jsonl **以任意顺序**拼接后重放，结果必须相等；重复重放同一份日志，结果不变（去重键 `(ts, origin, id, field)`）；同一写者连写两次 `todo → in_progress → todo`，日志必须留下两行，重放必须回到 `todo`。
>
> **性能（测 §9⑥ 的前置成本）**：500 节点合成库上，任意命令的兜底段 ≤50ms。
>
> **分支语义（测 §3）**：三个用例必须逐条给出预期结果并通过——在分支 A 建任务后切到 B（任务不存在，且不报错、不留幽灵）、把 B 合并回 A（任务与日志都并进来，日志行集合是并集且无冲突）、丢弃分支 B（B 上建的任务连同它的日志行一起消失）。

**这里删掉了一条旧的不变量**：v0.6 写的是「时间轴重放出的环节集合等于 `intent/` 现存节点集合（无遗漏、无幽灵）」。分支作用域定案之后它**必然为假**——union 合并会让日志里合法地存在其他分支创建、当前分支没有的节点。正确的说法只保留一半：

> **无遗漏**：磁盘上现存的每个节点都必须在日志里有对应的行。
>
> **允许有幽灵**：日志里有、磁盘上没有，是分支语义的正常结果，不是缺陷。`view` 把这类节点标为「其他分支」，`lint` 不报错。

### 替代验收（一次性）

> 迁移后 `intent/` 的森林结构与原 `exports/task-forest.graph.json` 的 `roots` / `tree_edges` **逐条一致**，且每个非空无映射去处的字段都出现在某个节点的 `## 迁移残留` 段里（不静默丢弃）。

v0.1 的 7 条验收标准里 6 条在测「能跑」、0 条在测「值得」，其中 2 条是「删掉 SQLite 后就不存在」的自洽性测试。**一部分工作量在证明另一部分工作量没出错，这是过度工程的操作定义。**

## 12. 已知的、未解决的风险

| 风险 | 现状 |
|---|---|
| **任务状态是分支作用域的。** `.hypha/` 被产品仓库跟踪后，切到任务创建之前的分支，任务就不存在 | **已在 §3 定为产品语义，不再列为「无缓解的代价」**；留在这里的是它的残余：跨分支的长期任务需要人**记得**放进 `~/.hypha/`（全局作用域），选错了没有报错。缓解是 `add` 在输出里提示当前作用域。真正无解的一小块见下一行 |
| **两条分支各改同一个任务的 `status`，合并时冲突。** 日志靠 `merge=union` 不冲突，frontmatter 是普通文本合并，会冲突 | **没有解。** 缓解是字段拆细、一行一字段，让冲突范围最小。单人多分支下罕见，多人下会常见——**这是「不做多写者并发」（§10.2）的边界之一** |
| **未提交的 `.hypha/` 变更会随 `git reset` 一起丢。** hypha 不自动提交，所以这个窗口真实存在 | `close` 按规则③输出可直接复制的 `git add` / `git commit`，`lint` 把未提交变更列成提示。**这是缓解不是解决**——根治需要自动提交，而那被法则三否掉了 |
| **`src/` 现在膨胀的是产品仓库。** 不可变来源若含 PDF、截图、大文本，全部进代码仓库的历史 | 这是这个选择里**唯一没有好答案的部分**。文本来源直接跟踪；`src/` 体积过阈值时 `lint` 报提示并建议走 LFS。若选择不跟踪大文件，机器 B 上 `anchors` 会指向不存在的文件，法则二随之削弱——这个取舍留给使用者，但**必须显式选，不能默认静默丢** |
| **快照日志单调增长。** 每次变更一行 | 按 task-forest 的 25 次变更外推，一年几万行是几 MB 量级，可接受。**但每行字节数目前是估计，不是实测**——迁移试跑之后用真实行长重算，写进 `tools/` 的度量脚本。按天分文件，老文件可归档；**归档必须整文件移走，不许改写行**，否则重放不再幂等 |
| **兼容路径仍会记录半成品。** 有人绕过 `apply` 直接 Write 正式节点后调 `boot` | 正常路径把草稿隔在 `.drafts/`，半成品不进索引。兼容路径仍记录而不丢历史，同时由 lint 标为未托管写入 |
| **整轮会话一条 hypha 命令都没调，则什么都不会发生。** 规则⑥的覆盖面是「下一次调用」，不是「下一次写入」 | 残留面比看上去小：`boot` 是拿上下文的唯一入口、`close` 是收尾入口，两头都近乎必然被调。**但「丢失面为 0」是错的，已撤回**——如果一条命令都没跑就 `git reset --hard` 或删掉文件，那段历史真的没了，因为它从未被写进日志。准确的说法是：**只要之后还会跑任意一条 hypha 命令，就不会丢**。宿主的 PostToolUse hook 可以让记录更及时，但**不能作为保障**——保障不该依赖宿主配置 |
| **`boot` 的条数上限是拍的。** know 段默认给 N 条 | 但拍错的代价被压到很低：删掉「正文前 200 字」后每条约 60 字符而非 260，尾部改成 opt-in（`hypha why <词>`），所以**拍小了只是多一次 `why` 调用，不是信息丢失**。真正会让 boot 膨胀的是 trigger 写得太宽，那是**静态可查的**——某个 trigger 命中 >20% 节点即噪声词，`lint` 报错。**截断是事后止损，lint 是事前防止** |
| **HTML 会重新长成 494KB 的怪物。** 「再多显示一点」是单调增长的压力，每一步都局部合理 | 体积预算已作废（正文必须内嵌）。防线改为 §5 的三条结构性约束，其中「不许给 schema 加字段」可机械检查，进自动化测试。**不靠自觉** |
| **多轮 `ingest` 协议会断。** agent 读 SKILL.md 判断 → 调 hypha 落盘，中间任何一步失败都可能留下半成品 | `lint` 是收网：半成品必然缺 `when` 或缺 `anchors`，两者都是 error。但**「断在哪一步」目前无恢复机制**，`ingest` 需要设计成可重入 |
| `~/.hypha/` 是唯一仍需单独同步的目标，也因此与 workspace 的 `.hypha/` 是两条时间线 | 建议 `git init ~/.hypha` 加私有 remote。跨仓库一致性不保证，但它只装 agreements 与跨 repo 知识，变化频率远低于 workspace。**两条时间线不做统一**——统一就得有一个中心，那是服务端（§10.2 明确不做）|
| LLM 判矛盾不可靠：版本演进、传递性矛盾、前提缺失冲突三种形态都逃出「两两比对」 | 四态 `conflicts` 是缓解不是解决。假阴性无解 |
| `when:` 会退化成「我是什么」或混入指令 | `when` 已退出机器匹配面；lint 只做同标题、换行和高风险措辞提示，boot 按不可信数据展示。真正的路由只由 `triggers` 决定 |
| 自动回填的 answers 页变噪声 | 靠 §11 主指标暴露；没被读的页应当删 |
| **§6 把零输入问题搬走了，没有证明它解决了。** 如果 agent 既不填 `affects` 也不写正文链接，任务的知识前提集同样为空 | `lint --audit` 对本轮变更给出候选关系和路由预演，agent 只需确认、拒绝或暂缓。仍以两周后的非空占比检验机制假设 |

### 一个已知正确但被推迟的答案

`.hypha/boot-log.jsonl` 记录了 boot 推荐过什么，主指标又要统计哪些被真的 `Read` 了。**这是个现成的闭环**：不必发明条数上限，用实测命中率反推截断点。

它和被三方处决的规则④（自我校准）机制相同，但**否决理由基本不适用**：样本是二元且直接观测的（Read 了没有）而非四因混杂，n 每天几十而非一年 20 个同类。唯一共享的缺陷是数据审查——截断变严后低分条目再没机会证明自己有用，标准修法是留一个随机探索位。

不进 Phase 1 的理由只有一个：它会把 boot-log 从「日志，丢了不影响正确性」变成**状态**，而「不引入需要重建承诺的状态」是这个设计删掉 SQLite 的同一条原则。所以推迟，但记在这里，不当作没想到。
